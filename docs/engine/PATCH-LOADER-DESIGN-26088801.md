# 数据文件路线的"加载器"：不需要执行权，只需要一个离线合成器

## 1. 旧加载器那套发现方法，确实不能用了

Bingus Shared Loader 的两件本事是绑在一起的：

* **执行权**：覆盖 `boot` 资源（id `murmur64("boot")` = `0xF476DF93691895FA`，活在包
  `9ba626afa44a3aa3` 里），让引擎自己加载它那段 LuaJIT 脚本 —— 这是唯一一个引擎会主动加载的 lua。
* **发现 mod**：拿到执行权之后，用 `ffi` 调 `kernel32` 去枚举 `data/*.patch_N`，再把找到的 mod
  逐个挂进运行时。

build 25988413 之后 `ffi` 没了，第二件本事直接断；第一件虽然还能做（boot 覆盖实测有效），
但跑起来的 Lua 已经**看不见文件系统、也改不了内存** —— 所以旧那套"枚举 + 注入"没了立足点。

## 2. 但我们的路线（改数据文件）根本不需要它

`patch_N` 是**引擎自己读的**：把 `data/<包名>.patch_N` 放在那里，引擎启动时按序号合并进对应包。
不需要执行任何代码，也不需要枚举 —— 引擎替我们做了。所以这条路线缺的不是加载器，是**共存**。

社区说"数据 mod 不能共存"，拆开是两条机制，两条都有实测依据：

| 机制 | 说明 | 依据 |
|---|---|---|
| **文件名撞车** | 每个 mod 都按 `9ba626afa44a3aa3.patch_0` 发布，后装的直接盖掉先装的 | 所有社区数据 mod 的包名/槽位都是同一个 |
| **序号必须连续** | 引擎按 `patch_0..patch_N` **连续**合并；中间缺号，**后面的一律不生效**（磁盘上文件在、md5 对，也当没看见） | `docs/engine/LOADER-SPEC-25988413.md`：把 patch_1/2 删掉只留 patch_3，探针 0/0/6 全 absent；连续时 3/3/3 |
| **序号是「每个宿主包各自从 0 连续」** | 不是全局序号：`<宿主A>.patch_0/1` 与 `<宿主B>.patch_0/1` 可并存；**给某个宿主装第一份补丁时，槽位必须从 `patch_0` 起** | 2026-11-01 反例：宿主 `f6fb08cc02d24255` 只有 `patch_2/3`（0/1 空），两份资源驻留补丁**静默不生效** —— 毒气/核爆粒子全缺失（表现为"有伤害无特效 / 呼叫无反应"）；改成 `patch_0/1/2` 后 `patch_compose.py scan` 报"空洞 无" |

第二条尤其阴：很多安装器"删除/重排补丁"时会在序列里留个洞，用户看到的现象就是
"两个 mod 一起装，有一个消失了"。**这跟 mod 内容无关，纯粹是槽位管理问题。**

## 3. 解法：离线合成器（`tools/patch_compose.py`）

在这条路线上，"加载器"应该做的事是：

```
scan     列出某个 data 目录里每个包的槽位与空洞（查"为什么不生效"）
merge    读多个补丁的条目 -> 按资源 id 求并集 -> 冲突检测 -> 合成一个补丁 + 回读验证
install  把合成结果放到该包的下一个连续槽位（拒绝在有空洞的链上安装）
```

判据（全部离线）：

* 同 id 同内容 → 去重；同 id **不同内容** → 冲突，默认拒绝合成（同一资源两个 mod 各写一份，
  语义上必须人工选边，`--prefer` 指定）；
* 合成后逐条回读，`toc` 与 `gpu_resources` 附流都要与来源逐字节一致；
* 安装前检查目标包槽位连续，只在**下一个连续槽位**写入。

### 实测（离线，用我们自己装着的两个补丁）

```
$ python tools/patch_compose.py scan --data "<game>/data"
9ba626afa44a3aa3: 槽位 [0, 1, 2, 3, 4]  空洞 无
  patch_0: 1 条 /  23,120 B  lua×1
  patch_1: 1 条 /  15,888 B  lua×1
  patch_2: 1 条 /   5,664 B  lua×1
  patch_3: 6 条 /   6,608 B  bones×1 material×1 texture×4
  patch_4: 1 条 / 418,432 B  lua×1

$ python tools/patch_compose.py merge --mods ...patch_3 ...patch_4 --out out/merged
并集 7 条；同内容去重 0 条；冲突 0 条
合成 out/merged/9ba626afa44a3aa3.patch_0  toc=421,232 B  gpu=2,272,056 B
  PASS 回读条目集合一致（7 条）
  PASS 逐条 toc 字节一致
  PASS gpu 附流一致
```

也就是说：**7 条异种资源（骨骼/材质/贴图/lua）能被合进一个补丁，内容不变** —— 这就是"共存"的
最低要求，而且全程离线可复跑。

## 4. ⚠ 还没定的四件事（都影响能不能真装）

1. ~~容器头的 28 字节~~ **已解（见 §7）**：那是 toc 头里 56 字节"未知元数据"的前半段，
   我们的 repack 因为"新建 Package 只塞条目"把它们（连带每条目的 blob 偏移）丢了，
   所以长度差 48 B。修好之后 `patch_3` 的 repack 已经**逐字节一致**。
2. **同 id 冲突时引擎谁赢**：是"后号覆盖前号"还是"先号优先"没测过。所以合成器默认拒绝冲突，
   不赌顺序。
3. **单补丁上限**：条目数 / 字节数有没有上限未知（现在最大的是 418 KB / 6 条）。
4. **多包**：`patch_N` 的连续性是**按包**算的。如果一个 mod 想改另一个包，就得各自一条链；
   跨包的合并策略还没设计。

## 5. 下一步（按代价排序）

1. 用合成器做一次**真装**：把两个小 mod 合成一个补丁装到下一个空槽，进游戏确认两个效果都在
   （这一步要启动游戏，等确认）。
2. 顺手把 §4.1 的 28 字节搞清：对比一个用 `srkit mod` 构建的补丁和一个社区补丁的头部，
   看哪些字段非零、是否与构建工具有关。
3. §4.2 的覆盖顺序：设计一个两行改同一资源的对照实验（两个补丁分别把同一字段改成不同值），
   进游戏看谁生效 —— 这条决定了合成器的冲突策略要不要支持"分层覆盖"。

## 6. BSL 那套协议能保留到哪一步：目录协议 ✅，运行时挂载 ❌

BSL 的"协议"其实是两层，拆开看就清楚了：

| 层 | BSL 怎么做 | 我们这条路线 | 结论 |
|---|---|---|---|
| **分发/目录协议** | `mods/` 下每个 mod 一个目录 + 清单，loader 读清单决定加载什么、什么顺序 | 完全可以照搬 | ✅ 保留 |
| **运行时挂载** | 拿到执行权后，用 `ffi` 枚举 `data/*.patch_N`，把资源挂进运行中的包 | 做不到：Lua 只能 `require` lua 资源，挂载数据包要引擎 API；`ffi` 已死；而且引擎是**启动时**按连续序号合并补丁的 | ❌ 换成"启动前部署" |

所以答案是：**能，但不是运行时加载器，而是"启动前部署器"**。做法是把 BSL 的目录协议搬过来，
在游戏启动前把它同步成一条连续的 `patch_N` 链。对玩家来说体验一样（放 mod、跑一次、开游戏），
只是这一次不是在游戏里跑，而是在启动脚本里跑。

### 6.1 mods 目录协议（照 BSL 的精神）

```
mods/
  <任意目录名>/
    mod.json          # 清单
    patch.dl          # 我们的补丁文件（原 patch_N，改名随意）
    patch.dl.gpu_resources   # 可选：附流，必须与 patch 同名
    patch.dl.stream          # 可选：同上
```

`mod.json`：

```json
{
  "name": "camera-probe",
  "package": "9ba626afa44a3aa3",
  "priority": 50,
  "patch": "patch.dl"
}
```

* `package`：目标包（现在都是 `9ba626afa44a3aa3`；不同包各成一条链，deploy 会按包分组）
* `priority`：越大越优先。**同一个资源 id 被两个 mod 各写一份时，高优先级赢**，并在日志里记一条覆盖。
  这是 BSL 时代不存在的问题（Lua mod 不抢资源），在我们这条路线上必须显式定义。

### 6.2 deploy 语义

```
python tools/patch_compose.py deploy --mods-dir mods --data "<game>/data" [--dry-run] [--prune]
```

1. 扫 `mods/*/mod.json`，按包分组、按 `priority` 降序；
2. 每组求并集（同 id 同内容去重；不同内容高优先级覆盖，逐条打印）；
3. **合成一个补丁，写到 `<包>.patch_0`**（附 `.gpu_resources` / `.stream`）；
4. 回读校验条目数与每条 `toc` 字节；
5. `--prune`：把该包其它槽位**先备份**再删除 —— 因为链上只剩 `patch_0`，"序号必须连续"这条规则
   天然满足，不会再出现"删了中间一个，后面全部失效"。

一个补丁装全部，是这个方案最关键的一点：它把"槽位管理"这个坑从根上去掉了。
代价是 mod 之间不再能单独启用/禁用某个补丁 —— 想禁用一个 mod，把它从 `mods/` 里移走重跑一次即可。

### 6.3 实测（离线，用我们装着的两个补丁当 mod）

```
$ python tools/patch_compose.py deploy --mods-dir tmp/mods-test --data tmp/fake-data --dry-run
包 9ba626afa44a3aa3: 2 个 mod（按优先级高→低）
  hd2runtime-lite   priority=100   1 条  <- patch.dl
  camera-probe      priority=50    6 条  <- patch.dl
  并集 7 条

$ python tools/patch_compose.py deploy --mods-dir tmp/mods-test --data tmp/fake-data
PASS 写入 9ba626afa44a3aa3.patch_0  toc=421,232 B gpu=2,272,056 B，回读 7 条
```

### 6.4 和 BSL 的真实差距（要说清楚，别让人误以为等价）

| 能力 | BSL（Lua mod） | 我们的部署器（数据 mod） |
|---|---|---|
| 放 mod 目录就能用 | ✓ | ✓（但要在启动前跑一次 deploy） |
| 游戏内热加载 | ✗（本来也要重启） | ✗ |
| 需要执行权 / ffi | ✓ 需要 | **不需要** |
| Steam 更新后 | 要等 loader 适配 | 要**重跑 deploy**（基础资源变了，补丁里的旧字节可能不再匹配） |
| mod 之间抢同一资源 | 不存在 | 由 `priority` 决定，日志可见 |
| 单独禁用某个 mod | 删目录重跑 | 移走目录重跑（补丁会重新合成） |

### 6.5 还能再往前一步（可选）

* 做一个 `start-modded.cmd`：先 deploy，再启动游戏（Steam 启动选项指过去，或桌面快捷方式）。
  对玩家来说这就是"加载器"的体验，但实现只是两行脚本。
* 反过来也可以提供 `--check`：对比当前 `data/` 里的 `patch_0` 与 `mods/` 目录的合成结果，
  不一致就提示"需要重新 deploy"（Steam 更新后最容易踩这个）。

## 7. 28 字节对照实验（已完成）

### 7.1 toc 头长什么样

srkit 的 `package.py` 写的很清楚，头固定 0x48 = 72 字节：

```
0x00 u32 magic = 0xF0000011
0x04 u32 type count
0x08 u32 entry count
0x0C u32 unknown
0x10 56 字节 unknown            ← 那"28 字节"就在这 56 字节的开头
0x48 类型表（每类型 32 B）| 条目表（每条目 80 B）| 各条目的 toc/gpu/stream 数据
```

### 7.2 实测：谁非零

| 补丁 | 大小 | 类型/条目 | 头 16 起的 56 字节 |
|---|---:|---|---|
| patch_0 | 23,120 B | 1 / 1 | 全零 |
| patch_1 | 15,888 B | 1 / 1 | 全零 |
| patch_2 | 5,664 B | 1 / 1 | 全零 |
| **patch_3** | 6,608 B | 4 / 7 | **非零**：`ce09f5f4 00000000 | 4bab91a040825ee7 | 0024e400 00000000 | 004b6800 …` |
| patch_4 | 418,432 B | 1 / 1 | 全零 |

用我们 srkit 写出并已被游戏接受的是 patch_0/1/2/4 —— **它们这 56 字节全是零**。
所以"零"对引擎是可接受的已知状态；patch_3 的非零值来自另一个写入工具。

### 7.3 决定性对照：`Package.parse` → `to_bytes` 逐字节还原

```
patch_3: 原 toc=6,608 重建=6,608 一致=True   gpu 2,885,188 -> 2,885,188 一致=True
patch_0: 原 toc=23,120 重建=23,120 一致=True
patch_4: 原 toc=418,432 重建=418,432 一致=True
```

**srkit 的写入器本来就能逐字节还原**。所以那 48 B 差异不是写入器的锅，是
`tools/resource_patch.py` 的 `repack` 写错了：它 `Package(name=BASE)` **新建**一个容器、
只把条目塞进去，于是丢掉三样东西：

1. 头里的 `unknown` 字段；
2. 偏移 16 起的 56 字节元数据；
3. **每个条目的原始 blob 偏移提示**（丢了就按 16 字节对齐重排，长度因此差 48 B）。

修好后的 `repack`（改成 `Package.parse` 原样读入再 `to_bytes`）对 patch_3 输出 **IDENTICAL**。

### 7.4 对合成器/部署器的结论

* **改写已有补丁**：必须原容器进、原容器出（现在 `repack` 已强制这么做）。
* **新建补丁**（我们的 `merge` / `deploy`）：这 56 字节写 0，与我们已被实机接受的
  patch_0/1/2/4 一致；不去抄某个 mod 的值，因为那串值到底是不是"条目内容摘要"没有证据，
  抄错比写 0 更危险。
* 仍然未知：那 56 字节的语义（哪个工具写的、引擎读不读）。要坐实只能做删改对照实验，
  但既然"全零"的补丁已被接受，**它不构成我们这条路的阻塞**。

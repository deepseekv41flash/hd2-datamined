# 投送舱换载荷：rack 槽位 · 双包声明 · 资源驻留（build `26088801`）

> **全程只改数据文件**（`generated_entities.dl_bin` + `generated_stratagem_settings.dl_bin`），不碰进程内存、不需要 Lua/FFI/注入。
>
> **一句话**：战备空投舱送什么 = `HellpodRackComponentData` 某条 rack 的槽位物品；
> 物品的网格/材质会不会画出来 = 战备行的 **`+0xA8`（包）** 与 **`+0xF8`（武器的 LoadoutEntry）**。
> 两个声明口 ⇒ **一次最多两个包**。

## 1. 结构

```
HellpodRackComponentData 0xA98BB156  @0x5E8E78, payload 43,768
  +0     2,304 B = ComponentIndexData 哈希图（144 槽 × 16 B，72 个键）
  +2304  41,464 B = 行数组（73 行 × 568 B）
```

每条 rack（568 B）：

| 偏移 | 大小 | 含义 |
|---|---|---|
| `+0` | 512 | `RackAttach[8]`，每个 64 B |
| `+512` | 4 | `LastRetractDelay` (f32) |
| `+516` | 1 | `DisableRetract` |
| `+520` | 8 | `MapIcon` |
| `+528` | 4 | `MapName` |
| `+532/536/540` | 4×3 | 音效 |
| `+544/548` | 4×2 | abilities |
| **`+552`** | 4 | **`random_payload_size`**（0 = 按槽序生成） |
| **`+556`** | 4 | **`spawn_payload_size`**（前 N 个槽生成） |
| `+560` | 1 | `DisableInitialInteraction` |

每个槽（`RackAttach`，64 B）：

| 偏移 | 大小 | 含义 |
|---|---|---|
| **`+0`** | **8** | **`Item` = 物品实体键（u64）** |
| `+8` | 4 | `Node`（挂点） |
| `+12` | 12 | `Offset` (vec3) |
| `+24` | 12 | `RotationOffset` (vec3) |
| `+36/40/44` | 4×3 | 动画事件 |
| `+48` | 1 | `apply_deltas` |
| `+52` | 4 | `rack_side` |
| `+56` | — | 未解 |

## 2. 槽位语义（决定改几个槽）

- 行号 = rack 号（本 build 73 行；rack 29 = StA-X3 W.A.S.P.）。
- **只有前 `spawn_payload_size` 个槽会生成**。StA-X3 = 2 ⇒ 只改槽 1、2 即可；槽 3、4 是「authored 但不生成」的重复项。
- 同一个 rack 可以被多个战备共用（本 build 有 6 个这样的 rack；StA-X3 **不是**其中之一）。
- ⚠ **清空槽位 ≠ 少生成一件**：引擎会跳过空槽、把后面 authored 的槽顶上来。
  实测把 rack 4 的背包槽清空后，舱里出现了**两把 AC-8**（槽 3 那件顶上来）。
  要少一件就改 **`+556`**（rack 行内 `+0x22C`），槽位数据一个字都不用动。

> 反面教训：一次实验里把槽 1–4 全换，结果与只换 1–2 完全一样 —— 因为 `spawn=2`。多改不会更糟，但也没用。

## 3. 换物品的配方（已实机）

```bash
# ① 换 rack 槽位（entities）
python tools/pod_rack_swap.py edit --rack 29 \
    --slot0 0x73D84EAAE8C75342 --slot1 0xB49756795D9B0E68 \
    --expect-old 0xCC786F6491FE7E65,0xB8FEB0CC191C1EF3 \
    --out entities.plain

# ② 声明包（stratagem）：+0xA8 给一件，+0xF8 给另一件的武器
python tools/plain_edit.py --plain generated_stratagem_settings.dl_bin --out strat.plain \
    --set "0xEC0C=u64:0x68F670405A504F68" \
    --set "0xEC5C=u64:0xF71F76BA"

# ③ 封装 + 部署
python tools/dlbin_seal.py seal-key entities.plain --key <recipient.pk> --out generated_entities.dl_bin
python tools/dlbin_deploy.py install --file generated_entities.dl_bin --sealed generated_entities.dl_bin
```

⚠ **偏移是按本 build 现算的，换 build 必须重算**：StA-X3 战备行基址 `0xEB64`（= `generated_stratagem_settings` 第 8 块，第 24 行，400 B 行），故
`+0xA8` → `0xEC0C`、`+0xF8` → `0xEC5C`。

`pod_rack_swap.py` 的门禁（任何一条不过都不写输出）：

| 门 | 检查 |
|---|---|
| G1 | 长度 = 原长 + pad + 8 |
| G2 | 差异 ⊆ 声明的 `Item` 字段 ∪ 末块 payload 尺寸字段 ∪ 校正字 |
| G3 | 重算 MurmurHash64A == 原始值（本 build `8E49771B181FFAA1`） |
| G4 | 每个 `Item` 字段读回 == 目标 |
| G6 | 容器重解析：块链自洽、空档 ≤ 8 B、结束点 == 文件长度 |
| G7 | 旧值 == 期望原版值（防改错行） |
| G8 | 校正字 8 对齐且不与 `Item` 重叠 |
| G9 | 追加区除校正字外全 0 |

**tail 宿主**：实体库是块序列容器（28 B 头：`u32 type | 'LDLD' | ver | type | payload | u8 wide | 7 rsv`），
与设置表的 24 B 头不同，所以不复用 `plain_edit.py`。做法同设置表：末块 payload 尺寸 += pad+8，文件尾追加 pad+8 零字节，校正字落在 `len+pad`（8 对齐）。

## 4. 资源驻留：两个包槽

> 这一节是摘要。**完整机制、解析链与边界见 [有限数量的跨包加载](../engine/LIMITED-CROSS-PACKAGE-LOADING-26088801.md)**；
> 一条命令完成整套改动的工具是 `tools/pod_loadout.py`。

引擎加载某个战备时，请求的是：

```
战备行的 +0xA8 包（toc 包 id）
  +  +0xF8 指向的武器的包（经 LoadoutEntry → 物品 → LoadoutPackage）
  +  原版物品自己的包
```

最后一条是「原版物品为什么两包也能渲染」的答案（Apex 舱 = 武器包 + 背包包）。

⇒ **换载荷时的判定表**：

| 换法 | 需要的声明 | 结果 |
|---|---|---|
| 只换一件，另一件留原版 | `+0xA8` = 新物品的包 | 两件都亮（原版那件靠自己的包） |
| 换两件、**同包** | `+0xA8` = 那个包 | 两件都亮 |
| 换两件、**不同包** | `+0xA8` = 一件的包，`+0xF8` = 另一件武器的 LoadoutEntry id | 两件都亮 |
| 换两件、不同包，只给 `+0xA8` | — | 一个亮、一个紫问号（**这就是「不驻留」的形态**） |

紫问号 = 引擎拿到了物品 id、但资源不在任何已加载的包里 ⇒ 一个免费的资源探针：
**没有** = 代码路径没走到；**紫问号** = 走到了但资源缺；**正常** = 资源在。

## 5. item → 包 解析表（`LoadoutPackageComponentData`）

```
0x7A858691  @0xA7E18, payload 35,232
  +0     17,600 B 哈希图（1,100 槽）
  +17600 17,632 B 行数组（551 × 32 B）
行： +0 u32  常量 0x1534F3FD
     +8 u64  ★ toc 包 id
     +16 u64 未解
     +24 u8 ×2（本 build 全 0x01）
```

键 = **物品实体键**（与 rack 槽里那个 u64 同一个空间）。

`+0xF8` 的解析：`+0xF8` 值是 `LoadoutEntryComponentData`（`0x4F2CF417` @`0xB07D8`，199 行 × 32 B，`+0` = id）的 **`+0` id**，
不是行号、也不是实体键。例：StA-X3 的 `+0xF8 = 0x351B2B3E` → LoadoutEntry 行 172 = W.A.S.P. 武器。

本 build 常用取值：

|---|---|---|---|
| GL-21 | `0x02EECD0B1FA49630` | `0x0089BBE3E284FCAA` | — |
| LAS-44 Nova | `0x73D84EAAE8C75342` | `0x601D726DE9C3962F` | `0xF71F76BA` |
| LIFT-182 Warp Pack | `0xB49756795D9B0E68` | `0x68F670405A504F68` | `0xC1E54B3A` |

| E | GL-28 / GL-28 背包 | GL-28 包 | 原版 | 都不带 | **两件都正常** |

> 污染排除：GL-21 与 B-1 的 `worldLoot = true`，会被地图随机刷新的同类物品顺带预加载 —— 第一次 B 轮就因此出现过「B-1 也正常」。此后一律改用 `worldLoot = false` 的物品（Nova / Warp / GL-28）才有干净读数。

## 7. 与 memmod 时代的关系

2026-10-09 的 `e1-stax3-pod` / `pod-rack-stax3` 用 Lua + ffi + `WriteProcessMemory` 写同样的两个 `Item` 字段，
但第三方 SDK 的记录明说：那份手写 payload 的**寻址是错的**（*"its addressing was not [correct]"*）。

所以本仓库**不是在复现一个成功案例，而是用一个可复算的寻址把它的意图做出来**。本次寻址全部从 typelib + 块几何 + 哈希图现算，
并被 SDK 的能力目录（rack 名、槽位占用、`spawn` 值）独立印证；同一份数据落盘后**重启不还原**，比当年更强。

## 8. 上限与「超过两个包」（2026-10-23 已解）

> 本节原来记的两条「未解」都已有结论，细节在
> [LIMITED-CROSS-PACKAGE §6.6](../engine/LIMITED-CROSS-PACKAGE-LOADING-26088801.md)。

- **「一个舱最多两件不同包」→ 已打破（✓✓ 实机 G 轮）**：
  战备表 153 行里 **133 行没填满**，空槽存量 155 个。把包铺到**进栏战备的空槽**上，
  引擎在**关卡加载时**就会请求它们 —— 一局最多 **16 个声明口**（4 个战备位 × 2 + 增援信标 4 + SOS Beacon 2 + 带鹰时 `EAGLE. REARM` 2）。
  实用版就是 G 轮：三个不同包 + 一个同包配件，四个槽全出。
- **整包资源驻留（补丁路线）→ ✓✓ 实机（2026-10-25 晚）**：把**整个包**的条目搬进
  `data/<宿主包>.patch_N`，宿主**不限注册表包** ——
  Warp Pack（50 条 / 3.5 MB）打进**共享基础包** `f6fb08cc02d24255.patch_0`、
  GL-28（51 条 / 2.7 MB）打进注册表包 `9ba626afa44a3aa3.patch_6`，
  舱里三件（Nova 走 `+0xA8`、Warp / GL-28 **零声明**）**全部正常渲染**。
  ⇒ 「整包驻留」不再受 16 口约束；声明口只剩"让引擎**主动请求**某包"这一个用途。
  细节：[RESOURCE-RESIDENCY](../engine/RESOURCE-RESIDENCY-26088801.md)（资源层驻留）。
- **`+0xA8` 写任意包 = 通用「预加载某包」开关 → ✓ 成立，但有前提**：
  只有**这一局出现在战备栏里**的那几发会被遍历（带上去就算，不需要叫出）。
  不在栏里的行（未携带的武器行、撤离信标）写了也不会被读。
- 改 `+0xF8` 是否影响战备的 UI（名字/图标）与本行授予的武器：本轮两轮都未观察到异常，但**未系统记录**。
- rack 几何：部分 rack 的槽 3/4 是占位节点（零偏移），把物品塞进去可能叠在一起 —— 只在 `spawn > 2` 时才有意义。
- 6 个 shared rack 改一处会影响多发布战备，需逐个确认。
- rack 62 的两个槽指向一个**没有 `LoadoutPackage` 行**的实体，其资源来源未解。
- `+0x40`（爆炸）与 `+0x56`/`+0x57`（槽内）等未知字段仍未解。

## 9. 溯源与许可

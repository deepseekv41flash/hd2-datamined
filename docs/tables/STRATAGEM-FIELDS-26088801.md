## 2. 面板公式（这才是玩家看到的数）

```
冷却时间 = +0x68 基础值 × 各冷却升级（相乘，取整）
           Eagle 额外 ×0.5（Liquid-Ventilated Cockpit）· 全体 ×0.95（Morale Augmentation）
呼叫时间 = +0x54 基础值 + 交付延迟 + 升级项
           交付延迟：ORBITAL +2.45 s · BACKPACK +4.75 s · EAGLE 见下 ⚠ · 其它 0
回收时间 = EAGLE. REARM 行的 +0x68 × 0.8（Pit Crew）× 0.9（Advanced Crew）× 0.95（Morale）
         = ×0.684
```

⚠ **投递延迟是「逐战备」而不是「逐类」**：同为 Eagle，Eagle Airstrike 面板 4.10 s、Eagle 500kg 面板 3.45 s，
而两行的 `+0x54` 都是 0 ⇒ 延迟不在战备行里，取值随战备而变。把它当"鹰式一类一个常数"会算错。

**四条都是先预测、后实测**（用户面板截图）：

| 实验 | 预测 | 面板 / 任务内实测 |
|---|---|---|
| 冷却：`+0x68` 写入 60 | `60 × 0.90 × 0.95 = 51.3` | **51 秒** ✓ |
| 呼叫时间：`+0x54` 写入 12.0（该用户有 −1 s 升级） | `12.0 + 2.45 − 1.0 = 13.45` | **13.45 秒** ✓ |
| Eagle 冷却：`+0x68` 写入 80 | `80 × 0.5 × 0.95 = 38.0` | **38 秒** ✓（§5.4.4） |
| Eagle 回收：`REARM +0x68` 写入 100 | `100 × 0.684 = 68.4` | **68 秒** ✓（§5.4.4） |

⚠ **推论**：不同玩家看到的冷却/呼叫时间**本来就不一样**（升级档位不同）。
判断改动是否生效，必须换回"基础值 × 该玩家升级"来核对，否则会误判成"没生效"。

## 4. `+0x3C` 不是"轮数"，是 **`StratagemCategoryType`**

### 4.1 假设怎么来的
"所有弹幕的值都是 5" ⇒ 猜它是 `salvos`（轮数）。

### 4.2 怎么否掉的
跨行统计全表 153 行：Eagle 类 = `0`、单发打击 = `1`、武器类 = `2`、弹幕类 = `5`
⇒ 它不是轮数。

### 4.2b 2026-10-28 定名：它是 `StratagemCategoryType` 枚举
`refs/web/generated_stratagem_settings.json`（社区解码的同一张表，103 项、带字段名）
与本 build 明文在 **102 行上都能对上**。把 `+0x3C` 的 u32 与解码字段 `category` 做双射：

| `+0x3C` | `StratagemCategoryType` | 行为上像什么 |
|---:|---|---|
| 0 | `CloseAirSupport` | 飞鹰空投 |
| 1 | `OrbitalFireSupport` | 轨道打击 |
| 2 | `HellpodDeployment` | 地狱舱投掷/空投（背包、支援武器、医疗包架…） |
| 3 | `TactialAirInsertion` | 载具空投 |
| 4 | `Special` | 信标/任务物件 |
| 5 | `OrbitalBombardment` | 弹幕/行走弹幕 |
| 6 | *（解码表里没有）* | 全表只 1 行：`SEAF Squad` |
| 7 | `CloseAirSupport` | 全表只 1 行：`EAGLE. REARM` |

⇒ **名字是 `category`，不是"投放方式"**；它之所以和投放行为高度相关，是因为分类本身就按投放方式分。
之前记成"投放方式"是按现象起的名字，现按数据校正。

### 4.2c 同一次双射还定死了另外 8 个字段

| 偏移 | 解码字段 | 命中 |

| `+0x90` | `triggers_war` | 102/102 精确 |

| `+0xBC` | `cost` | 102/102 |

| `+0xCC` | `max_in_loadout` | 102/102 |
| `+0xD4` | `beacon_color`（0 None / 1 Red / 2 Blue） | 双射 102 行 |

⚠ **`selectable` / `mission_specific` 这两个解码字段在本明文表里找不到对应存储**：
`mission_specific` 在 103 项里恒为 1（不可区分）；`selectable` 59/44 分布明确，
但逐字节 + u32 四 lane 全扫 102 行**零命中**（`b == 1+2*sel`、`(b>>1)&1` 也都试过）。
⇒ 它们要么在体量之外的层（运行期组件 / 账号状态），要么解码器自己推出来的。
想改「藏不藏」不能走这张表。

⚠ **`+0xA8 package` = 资源驻留声明，不能省**（2026-10-28 实机反证）：
修好载荷但不抄包 → **紫色问号**；同一补丁在配装里带上供体战备 → 正常渲染。
能用的行里 `package = 0`（`id 5` 照明弹 / `id 85` 机枪）之所以没事，是它们的载荷本就在基础包/配装包里。
**借来的载荷必须把供体的 `+0xA8` 一起抄过去。** 另一个声明口是 `+0xF8`（LoadoutEntry id，37 行支援武器在用）。

### 4.3 那次"轮数"实验为什么不能算证据
我们按 `+0x3C` 做过一次"改成 2 轮"的实验，**结果没变化**。但事后核对账本发现：
**当时部署的根本不是那个文件**（账本是另一个 probe）。
⇒ **这个实验作废**，它既不能证明 `+0x3C` 是轮数，也不能证明它不是。
⇒ **轮数本身仍然未验证**，只是位置指向弹幕组件的 `+0x18`。

**方法论教训**：说"已上机"之前，必须同时给出 ①账本里的 `installed_from` ②盘上回读值
③进程/转储状态。否则会拿一个没跑过的实验去否定一个正确的假设。

### 5.1 380mm 弹幕三项实机（2026-10-23）

基线（vanilla）：**每轮 3 发 × 5 轮 = 15 发**（与 wiki 的「15 发」吻合）· 壳间隔 1.5 s · 轮间隔 3.0 s ·
散布 36 m · 使用次数 无限 · 冷却 240 s · 呼叫 6.0 s。

| 实验 | 改动 | 预测 | 实机 |
|---|---|---|---|
| C 使用次数 | 战备 `+0x50` 无限 → 3 | 面板显示 3 | 面板「使用次数 **3**」✓ |
| A 轮数 | 弹幕 `+0x18` 5 → 1 | 基础 1 **+ 升级 +1** = 2 组 | 落 **2 组** ✓ |
| B 每轮弹数 | 弹幕 `+0x04` 3 → 1（轮数保持 1） | 2 组 × 1 发 = **2 发** | 全场只落 **2 发** ✓ |

⚠ **一个关键坑**：轮数也吃**升级**（存在「弹幕 +1 轮」的舰船升级）。所以判断改没改到，
必须按 `基础值 + 升级` 核对 —— 这也解释了当年「把轮数改成 2，结果还是落 6 轮」：那次改的是
战备行 `+0x3C`（投放方式），而**真实轮数 5 + 升级 1 本来就是 6**，数字完全对得上。

⇒ 至此战备侧**三个字段都有升级参与**：冷却（×0.90 ×0.95）· 呼叫时间（−1 s）· 轮数（+1）。

### 5.2 鹰式的 `+0x50` 是「每次回收次数」，不是生涯总次数

外部佐证（HD2Runtime `docs/stratagem-uses.md`）：

> The use count is `StratagemInfo` +80, a u32. The game's own unlimited value is `0xFFFFFFFF`…
> **Uses per rearm** — The eight Eagles. On Eagles the same field means uses per rearm, exposed as
> `hd2.fields.eagle.uses_per_rearm`, so `max_uses` is read-only for them.

⇒ 鹰式不是「任务里只有 N 次」，而是「每轮回收给 N 次」。改动前必须分清这两种语义。

### 5.3 ★ 鹰式的显示值走 **float32**：`+1` 升级 + 浮点精度决定一切

鹰式另有一条「使用次数 **+1**」升级，运行时**在显示前做加法**。把这组值一次灌进 8 个鹰式、
一次重启读完面板，得到完整曲线：

| 写入 `+0x50` | 面板显示 | 说明 |
|---|---|---|
| 10 | **11** | `+1` 生效 |
| 100 / 1,000 / 10,000 / 1,000,000 | 101 / 1,001 / 10,001 / 1,000,001 | `+1` 仍精确 |
| **16,777,216（2²⁴）** | **16,777,216** | `+1` **被舍掉** ⇒ float32 尾数 24 位 |
| 268,435,456（2²⁸） | 268,435,456 | 该量级间隔 32，`+1` 全丢 |
| 3,000,000,000 | 3,000,000,000 | 恰为 256 的倍数 ⇒ 精确表示 |
| 4,294,967,167 | **4,294,967,040** | 下舍到 256 倍数，**仍算"原值"** |
| **4,294,967,168** | **0** | 上舍到 2³² ⇒ 转回 u32 **回绕**（**这就是边界**）|
| 4,294,967,293（0xFFFFFFFD） | **0** | 同上 |
| 0xFFFFFFFE / 0xFFFFFFFF | **0** | 同上 |

**⇒ 鹰式次数没有「引擎校验上限」，实际可用上限由 float32 精度决定：`2²⁴−1 = 16,777,215`。**
超过它只是显示失真；接近 2³² 会回绕成 0（等于不能用）。

**「原值 → 0」的确切门槛 = `2³² − 128 = 4,294,967,168`**（半 ulp 的舍入中点）。

float32 在不同量级的间距等于 `2^(e−23)`：`[2²⁴,2²⁵)` 是 2、`[2²⁸,2²⁹)` 是 32、`[2³¹,2³²)` 是 **256**。
所以 2²⁸–2³² 这一段并**不是**"都变 0"，而是**整段都显示原值**（只是被量化到间距的倍数）；
只有舍入结果触到 **2³²**（本身可被 float32 精确表示）时，转回 u32 才回绕成 0。

实测锚点（相邻两值夹中点，一次重启验证）：
`4,294,967,167 → 4,294,967,040`（下舍）而 `4,294,967,168 → 0`（上舍）。


对照：**非鹰式**（轨道类）写 `0xFFFFFFFF` 正常显示「无限」 ⇒ 两条路径实现不同：
非鹰式**先特判 sentinel 再转换**，鹰式直接进浮点运算。所以「鹰式也设无限」这条路**不通**。

⚠ 附带事实：鹰式面板**次数 = 0 或 1 时不显示冷却**（「不适用」），次数 > 1 才显示（实测 7 秒）。

| `+0x188` | `7` | 面板格 | 与空袭行同格 |

合理性核对：wiki 写 Eagle 回收 150 s，Pit Crew Hazard Pay（−20%）= 120 s，Advanced Crew Training（再 −10%）= 108 s
⇒ 就是 `150 × 0.8` 与 `150 × 0.8 × 0.9`，与我们已验证的"冷却升级相乘"模型**同构**。

#### 5.4.3 双目标实机（2026-10-23，一次封装改两行）

```
python tools/stratagem_tune.py --plain <work>/generated_stratagem_settings.dl_bin \
  --edit "EAGLE. AIRSTRIKE::cooldown=4" \
  --edit "EAGLE. REARM::cooldown=5" \
  --out <work>/out.plain.dl_bin
```

| 项 | 结果 |
|---|---|
| 整文件差异 | **5 字节**（两个 f32 各 2 B + 末组 `payload_size` 1 B），82,384 → 82,392 B |
| 哈希 | `0x04BBE33EF809862A` 保持不变，G1..G7 全过 |
| 封包往返 | 82,440 B，`open-key` 解回与明文逐字节一致 |

**两处独立读数，把"字段是活的"和"这一行被消费"分开了：**

| 观测点 | 改动前 | 改动后 | 判定 |
|---|---|---|---|
| 面板「冷却时间」（Eagle Airstrike） | 7 秒 | **2 秒** | ✓ `+0x68` 是运行时活字段 |
| 任务内回收等待 | 150 秒 | **3 秒多** | ✓ `EAGLE. REARM` 行**确实被引擎消费** |
| 面板「呼叫时间」 | 4.10 秒 | 4.10 秒 | = `+0x54`(0) + Eagle 投递延迟 **4.10**（⚠ 该延迟逐战备不同：500kg 是 3.45） |
| 面板「使用次数」 | 3 | 3 | = vanilla 2 + Expanded Weapons Bay **+1** |

⇒ **这是"面板不可见字段"的验证范式**：先用一个面板可见的同类字段（`+0x68`）证明写入链路通，
再单独用任务内计时去证被改的那一行真的被读。否则"没变化"无法区分"没改到"和"没被读"。

#### 5.4.4 收口实验：两个 ⚠ 全部解开（2026-10-23 第二 / 第三轮）

第一轮留下的两个问题，都用同一个办法解决：**选一个能把两种假设分开的基值**，而不是靠肉眼看小差别。

**① Eagle 面板冷却公式**（第一轮只有 base 15→7、base 4→2 两个点，两个模型都吻合）

| 模型 | 公式 | base 15 | base 4 | **base 80（判决点）** |
|---|---|---|---|---|
| **A** | `round(+0x68 × 0.475)` = **×0.5 ×0.95** | 7.125 → **7** ✓ | 1.9 → **2** ✓ | 38.0 → **38** |
| B | `floor(+0x68 / 2)` | 7.5 → **7** ✓ | 2 → **2** ✓ | 40 |

实测（Eagle 500kg，冷却是 80）：面板「冷却时间」= **38 秒** ⇒ **模型 A 成立**。

⇒ 那个来路不明的"÷2"不是一个硬编码除数，而是**两个真实升级相乘**：
`×0.5 = Liquid-Ventilated Cockpit`（Eagle 冷却 −50%）、`×0.95 = Morale Augmentation`（全体战备 −5%）。
base 80 之所以能判决，是因为 80 × 0.475 = **38.0 恰好是整数**，没有任何舍入歧义。

**② 回收时间的升级系数**（第一轮 "base 5 → 3 秒多" 落在三种假设的区间内，分不开）

把基值从 5 拉到 **100**，三个候选立刻分开：

| 假设 | 系数 | 100 × 系数 | 预测 |
|---|---|---|---|
| 只有 Pit Crew Hazard Pay | ×0.8 | 80 | 80 秒 |
| ＋ Advanced Crew Training | ×0.72 | 72 | 72 秒 |
| **＋ Morale Augmentation** | **×0.684** | 68.4 | **68 秒** |

实测：任务内回收 = **68 秒** ⇒ **三个升级全部相乘**：`×0.8 × 0.9 × 0.95 = ×0.684`。
回头验 base 5：5 × 0.684 = 3.42 → "3 秒多" ✓ 一致。

⇒ **面板冷却与回收时间用同一套「相乘」模型，只是升级集合不同**：
冷却吃 Liquid-Ventilated ×0.5 + Morale ×0.95；回收吃 Pit Crew ×0.8 + Advanced Crew ×0.9 + Morale ×0.95。

⚠ 取整规则仍未分辨：68.4→68 与 3.42→3 在 floor / round 下同值。要分辨就把基值取到 x.5 附近
（例：base 125 → 85.5，floor 得 85、round 得 86）。


## 6. `+0x00` 是**连续 1 基条目 ID**，不是枚举 —— 重复 = 崩溃

- 153 行，`+0` 恰好是 `1..153` 的排列（无空洞、无重复）。
- 复制一行时**沿用原 ID** ⇒ 重复键 ⇒ 引擎解引用未初始化槽 ⇒ **三次完全相同的崩溃**：
  `0xc0000005 @ game.dll+0x1083a45`，会话寿命 26–29 秒。
- ⇒ 新增行必须 `+0 = 最大 ID + 1`；`stratagem_struct.py --assign-next-id` 已实现。

## 7. 与爆炸链的衔接

```
战备行 +0x98 ──► 实体哈希数组 ──► generated_entities 组件块（弹幕 / 包 / 破片 …）
弹丸行 +0x90 ──► 爆炸 type（命中）· +0x9C ──► 爆炸 type（到期）
爆炸行 +0x38 ──► 粒子资源 · 战备 +0xA8 ──► 该资源所在包
```

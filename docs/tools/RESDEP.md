# resdep.py —— 资源依赖自动追踪（粒子 / 实体 / 声音）与驻留计划

> 起因：社区同行的更新日志（2026-10-27）把踩过的坑写得很清楚——
> 「资源驻留原来只按**射弹所属装备**猜测来源包，会漏掉实际**粒子**依赖」；「缺失粒子阻止安装，未定位音效明确提示，
> **不把写入成功等同于游戏音效已验证**」；「反查装备归属使用**原始基准**，避免用户已修改的数据污染归属」。
> 这个工具把"扫引用 → 解析到资源 → 落到包 → 出驻留计划 → 缺失即拦"做成一串命令。

## 1 四个子命令

| 命令 | 做什么 | 本 build 实测 |
|---|---|---|
| `index` | `srkit list --json` 拉全档清单（**约 20 秒**），建 `资源 id → {类型, 名字, 宿主包}` 索引，缓存到 `refs/resdep/` | 322,810 行 / **62,915** 个去重 id / 3,427 包 → G1 PASS |
| `chain` | 从 `--weapon` / `--entity` / `--explosion` 走引用链，对每一行做**全 u64 扫描**并解析 | 爆炸 213：粒子 + 震屏，9 包，**0 缺失** |
| `plan` | 以**目标件自己声明的包**（`LoadoutPackage+0x08`）为基准，把叶子分「同包 / **跨包** / 缺失」；缺失默认**拒绝出计划**；产出 `plan.sh` | MG-43：同包 7 条 / **跨包 11 条（5 包）** / 0 缺失 |
| `sound-catalog` / `sound` | 解 wwise bank（16 B 包装头 → BKHD/DIDX/DATA/**HIRC**）建 `事件 id → bank` 目录；查单条事件 | 3 个 bank 样本 → 100 个事件；全量 641 bank ≈ 23 分钟 |

```bash
python tools/resdep.py index                     # 一次性（20 s）
python tools/resdep.py chain --explosion 213
python tools/resdep.py chain --weapon "MG-43"    # 名字或 0x 实体 id 都行
python tools/resdep.py plan  --weapon "MG-43"    # 出 out/resdep/plan/plan.sh
python tools/resdep.py sound-catalog             # 建事件目录（可先 --limit 5 试）
python tools/resdep.py sound --event 0x0153E8DE
```

## 2 为什么"不猜字段"也能找全（方法）

一个 u64 只要能在 **322,810 行的资源清单**里命中，它就是这个资源的 id——所以**扫全行**比"猜这个字段是粒子"可靠：

- 命中概率极低（62,915 个 id / 2^64），几乎不会有假阳性；
- 因此**不需要预先知道偏移**：新字段、嵌套结构、破片/电弧引用都能被扫出来；
- 已证字段再加标注，方便读：实体 `Unit+0x00`、`EffectReference`（粒子/生成单位/震屏三张表）、
  爆炸行 `+0x38`（粒子 file_id）、`+0x28/+0x30`（震屏表：**payload 相对偏移**，别当绝对偏移用）。

## 3 本 build 实测到的两个硬事实（`✓`）

1. **爆炸行的粒子是完整的 64 位 file_id**，不是 32 位 id：
   424 行里 **331 行**的 `+0x38` 恰好命中 `particles` 类型资源；其**高 32 位**就是我们文档里记的那些 32 位粒子号
   （例：type 343 的 `+0x3C = 0xA82CA988`，整 u64 = `0xA82CA988F7A100D1`）。
   ⇒ 以前"按 32 位号去猜包"必然漏，因为真正的键是 64 位。
2. **震屏表用 payload 相对偏移**：`payload_at = head + 28`（本表 head=0 ⇒ 28）。少加这 28 会让整表读歪，
   读出"两个共享高 32 位的怪 id"——这正是"漏依赖"的典型来源。

## 4 门禁与结论分级

| 门禁 | 判据 | 不过时 |
|---|---|---|
| G1 | 清单行 > 100,000 且去重 id > 40,000 | `index` 返回 1（索引没拉全） |
| G2 | 每个叶子资源都能解析到包 | 报告里逐条列出 |
| **G3** | 缺失资源 → **拒绝出驻留计划** | 返回 2；`--allow-missing` 才降级（等于承认要装占位/灰块） |
| G4 | 补丁序号连续 + `.gpu_resources`/`.stream` 伴生齐全 | 打印 FAIL 与下一个可用序号 |
| G5 | 声音目录缺省不阻塞；命中才写"已登记" | 未定位只提示 |

**三级结论不混**（照社区那条纪律）：① 资源解析到了 ≠ ② 驻留写进去了 ≠ ③ 游戏里表现对了。
`resdep` 只保证 ①；② 由 `whole_package_patch.py` 的 G1–G8 保证；③ 只有实机能证。

## 5 已知限制（`⚠`）

- **`unit` 资源在清单里是 `type=mesh, codec=unit`**，不是独立类型；按 `--type unit` 过滤会空手。
- 同一资源常在**多个层包**里有副本（一个粒子 8 个包很常见）。`plan` 会优先挑"已在盘上补丁/基础包"的那份，
  否则取第一个——想指定就加 `--assume <包>` 或在 `plan.sh` 里手工调整。
- 角色/单位那一侧的依赖（骨骼、状态机、动画）能扫到 id，但**是否真的随场景加载**仍要看实机（同 R1 规则）。
- `sound-catalog` 全量约 23 分钟（每 bank 约 2 秒），目录缓存到 `refs/resdep/`，只需建一次。

## 6 与既有工具的关系

- `whole_package_patch.py`：`plan.sh` 里生成的就是它的命令（整包驻留，host `f6fb08cc02d24255`）；
- `entity_field_set.py` / `plain_edit.py`：改字段（保 murmur64）；
- 三者串起来就是一条完整闭环：**改字段 → resdep 看漏了什么 → 整包驻留 → 实机**。

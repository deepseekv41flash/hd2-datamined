# PLAYBOOK：老版本 Lua mod → 数据路线（`.dl_bin`）等价「修复版」

> **固定流程**：**只读侦察** → **判断能不能用数据路线等价** → **能就做出等价修复版**。
> 适用于任何第三方 HD2 mod（zip / `patch_0` / 已装补丁），不限于 Lua。
> 三个样板案例见 §6；工具见 §4；跨 build 的坑见 §5。

---

## 0 输入 / 产出 / 硬规则

| 项 | 内容 |
|---|---|
| 输入 | 第三方分发包（`.zip`、`9ba626afa44a3aa3.patch_N`、或已装进 `data/` 的补丁） |
| 产出 A | **已做出修复版**（封包 + 装盘 + 回读 + 三态） |
| 产出 B | **A · dl_bin 等价** 或 **B · 跨载体等价**：给字段/资源 + 命令（不装盘） |
| 产出 C | **C · 不可实现**（指明卡在 L4 与卡点，给最接近的替代） |
| 硬规则 | ① 侦察阶段全程只读（不写游戏目录、不碰进程内存）；② 任何写入必须保哈希 + 门禁 + 回读 + 一条命令可回滚；③ 结论必须带三态与证据路径 |

## 1 五步流水线

| 步 | 动作 | 工具 / 命令 | 产物与判据 |
|---|---|---|---|
| **1 开包** | 列出 `patch_0` 里的条目，抽 `lua` 载荷，**字节码壳自动解码** | `python tools/lua_payload_dump.py --patch … --out …`（`--zip` 也行） | 载荷清单表：`id / 形态(source\|bytecode) / 大小 / 关键词命中` |
| **2 读载荷** | 源码直接读注释与常量；字节码读 `*.strings.txt`（表名、字段名、报错文本都还在）；**再看有没有作者源码树** | 文本阅读；megapack 那种 `Generated by build.py from src/…` 指向仓库里的 `src/*.lua`，有源码 = 证据升级 | 能列出它**每一次写入**的目标（表/组件/资源/代码） |
| **3 归层** | 把每处写入归到 §2 的 L1–L4 | — | 一张"写入 → 层"表 |
| **4 映射** | 每个写入找**我们 build** 的对应物：容器 type id、行键、字段偏移、枚举值 | `table_dictionary.py`（typelib 字段图）、`entity_field_set.py show`、`dmg_row_edit.py show`、`refs/entity-locid-names.json` | 1:1 映射表；**必须用我们的明文表反推，不许照抄 mod 里写死的常量** |
| **5 实现 + 验证** | 保哈希编辑 → 封包 → 装盘 → 回读 →（实机） | §4 的工具矩阵 | 门禁全 PASS + 封包 sha256 + 盘上回读 + 三态表 |

## 2 分层矩阵：先看**载体**，再谈可不可能

⚠ **用词纪律**：不要说"不可等价"。能不能做取决于**换哪个载体**，
我们至少有三条能落地的载体（dl_bin / 资源包 / 实体 delta），只有引擎代码与进程内存是死路。

| 层 | 老 mod 的典型写法 | 我们的等价载体 | 判定 |
|---|---|---|---|
| **L1 数据表**（settings） | 内存里找 `generated_*_settings` 缓冲，改行内字段/位 | 同名 `.dl_bin` 的同一行同一字段 | **A · dl_bin 等价**（首选） |
| **L2 实体组件** | 组件块 hashmap → 行 → 字段 | `generated_entities` 的组件块；跨包/增量写 `generated_entity_deltas` | **A · dl_bin 等价** |
| **L3 资源** | 改 havok 材质 `userData`、换 unit/mesh、换粒子/贴图/材质 | **资源路线**：`srkit` 解包 → 改载荷 → `patch_N` 资源包（+ 跨包驻留） | **B · 跨载体等价**（dl_bin 做不到，但资源能做到） |
| **L4 引擎代码/内存** | 改 `.text`、hook 函数、运行时 `WriteProcessMemory` | 无（我们只交付盘上数据/资源） | **C · 不可实现** |

**载体能力表**（这些资源族我们**已经做过**，不是"理论上可以"）

| 资源族 | 我们已做到什么 | 出处 |
|---|---|---|
| `physics`（Havok 2019.01 tagfile） | 逆出载荷布局（`TAG0`/`SDKV20190100`/`TBDY`…），**质量字段 marker `0x4A182741` + flags + f32 mass**，全库 431 份交叉验证；改 mass 实机生效 | `docs/cases/CASE-STUDY-20261021.md` §17–§18 |
| `texture` / `material` | 贴图十连换（10× APEX），材质与资源覆盖流程成型 | `docs/cases/TEXTURE-SWAP-10X-APEX.md`、`RESOURCE-OVERRIDE-TYPES-26088801.md` |
| `particles` | 全库普查 + 按 file_id 抽取（`particle_census.py`）；确认参数不可由表改，须资源路线 | `docs/tables/WEAPON-FIRE-MODES-26088801.md` §5.6.7 |
| `unit` / `mesh` / `geometry_group` | 壳替换、几何提取、空壳模板（`srkit emptyunit`） | `docs/cases/CASE-STUDY-20261021.md`、`docs/engine/*` |
| 打包/部署 | `srkit pack` 出 `patch_N`、Bingus/官方两条装配路 | `skills/hd2-mod-maker`、`srkit-resources` |

**判定口径（三档，按载体命名）**

| 判定 | 含义 | 交付 |
|---|---|---|
| **A · dl_bin 等价** | 每处写入都落在 L1/L2，且有 1:1 字段 | 直接做修复版（保哈希 → 封包 → 装盘） |
| **B · 跨载体等价** | 关键写入在 L3：dl_bin 里没有，但**资源族里有且我们能改** | 给资源路线配方（定位资源 → 改载荷 → `patch_N`），必要时先做**只读样本证明** |
| **C · 不可实现** | 落在 L4（引擎代码/运行时内存），且无等价载体 | 说明卡点 + 可替代的"最接近效果" |

> B 档内部要再标**置信度**：该资源族已有实证（如上表）= **高**；
> 同族但没有针对这一条验证过 = **中**（写成"资源路线可行，⚠ 未针对本条验证"）。

## 3 反例优先：先证明"它没改什么"

侦察最容易犯的错是"名字像就以为改的是它"。两个实例：

| mod 名 | 直觉 | 实际 |
|---|---|---|
| `StickyGrenadeHandles` | 改 `StickyComponentData` | ✗ 改的是 **物理材质库**里 `sticky_grenade_handle` 的 `userData`（4 B）；`ThrowableComponent +0x54/+0x164` 只读校验 |
| `BetterStratagemBounce` | 改投掷/粘附 | ✗ 改的是**战备表每行 `+0x170`** 的一个 bit |

⇒ 报告里要显式写一行「**它没有碰 X**」并给证据（写入点清单）。

## 5 跨 build 的「修复版」规则（**最容易翻车的一步**）

老 mod 全都带"只对某个 build 成立"的写死常量。做修复版时必须逐类重取：

| 常量类别 | 老 mod 的形态 | 我们的做法 |
|---|---|---|
| **字段偏移** | `STICKY_MATERIAL = 0x164` | 从 typelib 现场取（`table_dictionary.py`），并用 `entity_field_set show` 实证 |
| **期望值表** | `vanilla_flags = {2,2,0,…}`（按 kind 索引） | **从我们的明文表现算**，绝不照抄（本轮实测 74/148 不匹配） |
| **对象集合** | 写死实体 key（`lo/hi` 两段） | 用 `refs/entity-locid-names.json` 按**名字**反查 id |
| **行号/行数** | `records == 149`、`103 changes` | 现算行数与"会被改的行"清单，写进报告 |
| **校验式** | "不等于期望就拒绝执行" | 数据路线改成：**先 dump 原值 → 只改声明字段 → 门禁比对**（不做全局相等断言） |

### 6.1 C 档样板（代码型）：P-11 Self-Heal —— 老 mod 是运行时事件，数据只能做替代

**老 mod 是什么**：`P-11 Self-Heal v1.0.4`（`D:/Downloads/P-11-Self-Heal-v1.0.4.zip`）。
它**没有改任何数据、没有写内存** —— 订阅运行时的 `player_fired` 事件（运行时每 0.1 s 轮询游戏的
`projectiles_fired` 统计，带每把武器的射击数），命中 P-11（资源 hash `0xD6B1FB05B9109353`）后调
`player:heal()`（内部走游戏 `AddHealthFraction`），可选 `hd2.actions.heal_limbs` 修部位。
413 行源码 + README 互证，全文无写入原语。

**① 卡点定位**

| 需要什么 | 数据侧有没有 | 结论 |
|---|---|---|
| 开火事件（"本地玩家打了一发 P-11"） | **没有**：数据表没有"每次开火自动施加状态"的字段 | 卡在 L4 |
| 调用引擎治疗函数 | **没有**：数据只能提供"伤害行 → 状态槽"这种载体，不能主动调用 | 卡在 L4 |
| 资源路线（L3） | 无等价载体：事件订阅与函数调用不是资源属性 | — |

**② 最接近替代（已交付，✓ 实机）**

| 替代 | 做法 | 实测 |
|---|---|---|
| 数据侧**治疗爆** | 孤儿爆炸 **254**（半径 1.4/1.5/2.0 m）+ 伤害行 **446**（全零 + `slot0=(29 Stim Pistol Heal, 1.0)`）；P-11 弹丸 `+0x90/+0x9C = 254` | 打自己脚下 → **回血、不受伤**；**>2 m 打地面 → 不回血**（两个方向都测） |

**③ 残余差距（用户能感知的差别）**
- **要打脚下**（落点在自己 2 m 内），不是"打一发就治"。
- **部位损伤 → ✓ 实机**（状态 29 会顺带修部位，2026-10-25 用户实测）；**加速 / 耐力仍 ⚠ 未验**（状态 29 的完整语义）。
- 剂量可调性从 cfg 变成数据表（状态强度 / 半径 / 换任意武器反而更自由）。
- 反转要写清：README 说运行时**不允许**施加 stim 状态，而数据路线施加的正是状态 29 —— 能力面各有胜负。

**④ 这个案例的教训**：C 档不是"功能做不到"，而是"**这个形态**做不到"。写报告时把
「机制卡在哪」和「替代能做到什么」分成两栏，别混成一句"不可实现"。

### 6.2 C 档样板（数据边界型）：锁定锥角 / 可锁目标集合

两个 C 档样板之一（另一个是 §6.1 的 P-11 Self-Heal，**代码型**；这里是**数据边界型**：数据表在，但引擎不读）。
判断标准只有一条：**卡点必须真的在 L4**，否则会翻档 —— 例如 P-11 治疗爆一度被当成 C，
其实只是"数据里有没有载体"的问题，最后翻成 A（见 [STATUS-EFFECTS §7.4](../tables/STATUS-EFFECTS-26088801.md)）。

**需求**：放宽或取消锁定武器的「锁定锥角」、扩大「可锁目标集合」（让 P-92 / Spear 想锁谁锁谁）。

**① 卡点定位（逐层排除，每行都有实测/离线结论）**

| 层 | 试过什么 | 结果 |
|---|---|---|
| L1 dl_bin | `GuidanceTarget +0x20 target_lock_dot` 0.95→0.5 | **✗ 否证**（锥角没变） |
| L1 dl_bin | `SensorEye +0x0C/+0x10 angle_h/v` 20→90 | **✗ 否证** |
| L1 dl_bin | 两者同时放宽（合取模型） | **✗ 否证** |
| L1 dl_bin | `SeekingMissile +0x54 MaxAngleToTarget` 45→120 | **✗ 否证**（那是发射后制导限制） |
| L1 dl_bin | 标签位图里加「可锁」位 | **✗ 不可读亦不可改**（4352 bit 位图，无「位↔名」映射） |
| L1 dl_bin | `SeekingMissile +0x00 TargetingMode` | **✗ 不在数据里**（同一 mode 内目标过滤仍不同） |
| L3 资源 | — | **无等价载体**：锥角与过滤是引擎判定，不是资源属性 |
| **L4** | — | **卡点在这里**：锁定判定逻辑在引擎代码里 |

**② 最接近替代（已交付，✓ 实机）** —— 把「放宽锥角」换成一远一快：

| 替代 | 字段 | 实测 |
|---|---|---|
| 锁定**距离** | `SensorEyeComponentData +0x00 distance` | P-92 60 → **300 m**：**✓ 实机**（能锁 60 m 以外的目标） |
| 锁定**所需时间** | `GuidanceTargetComponentData +0x10 lock_on_target_time` | Spear 1.00 → **0.05**：**✓ 实机**（用户原话「几乎是一瞬间」） |

组合体感 =「**更远 + 一瞄即满**」：仍要大致对准，但"对准成本"被距离和速度吃掉了大部分。

**③ 残余差距（必须诚实写）**
- 仍要**大致把准星压到目标附近**；`dot` 的实际判定没变。
- **不能锁「本不可锁」的目标**（位图不可读 ⇒ 纯试错且无判据）。
- 每把武器自己的过滤（Spear 只锁建筑/精英）照旧。

**④ 可复用的 C 档写法**：`逐层排除表（每行带结论）→ 一句话说清卡在 L4 的什么逻辑 →
最接近替代（带实测值，不能只是"建议"）→ 残余差距（用户到底差在哪）→ 别再花局验的清单`。

## 7 报告骨架（照抄这个结构）

```
# 只读侦察：<mod 名> v<版本>
> 一句话结论：它改的是 <层><表/资源>；我们 <能/部分/不能> 等价。

## 1 包结构        （zip → patch_N → 条目 → 脚本形态）
## 2 它改了什么    （每次写入一行：目标/偏移/旧值/新值；含"没碰什么"）
## 3 本 build 对照 （字段映射表 + 老表 vs 现算，差异列出）
## 4 能否等价      （L1–L4 判定 + 若可等价的配方/命令）
## 4b 若不可等价   （卡点 + 最接近替代 + 残余差距；见 §6.1 / §6.2）
## 5 修复版产物    （封包 sha256 / 门禁 / 盘上回读 / 回滚命令）
## 6 三态          （✓ 离线 / ✓ 实机 / ⚠ 未证 / ✗ 否证 逐条）
```

## 8 三态

| 结论 | 态 |
|---|---|
| 开包→抽载荷→字节码壳解码 已工具化 | **✓ 离线**（`lua_payload_dump.py`，三个真实 mod 实测通过） |
| 判定分三档（dl_bin 等价 / 跨载体等价 / 不可实现），**不再用"不可等价"** | **✓ 方法论**（L3 有资源族实证，见 §2 载体能力表） |
| "先证明它没碰什么"能避免误判 | **✓ 离线**（两例名字误导） |
| 数据路线修复版的实际观感需实机确认 | **⚠ 待实机**（`heal29` 已装盘待测） |
| 「C 档」有填满的样板（卡点 + 替代 + 残余差距） | **✓ 方法论 + ✓ 实机**（[LOCKON §7.5](../tables/LOCKON-TARGETING-26088801.md)：锥角 ✗、距离/时间 ✓） |

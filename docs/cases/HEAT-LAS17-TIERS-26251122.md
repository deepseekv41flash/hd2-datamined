# LAS-17 高/中/低热档换弹丸：热量机制全解（build `26251122`）

> **一句话**：激光武器的"弹匣"是热量槽（`WeaponHeatComponentData`）。**LAS-17 是全游戏唯一**把热量组件里
> 3 组 `HeatLevelSetting` 填了值的武器——每组 = `{温度阈值, 该档换用的 ProjectileType, 挂给持枪者的 StatusEffectType}`。
> 引擎按当前热量选"阈值 ≤ 热量"的最高档，把**这一发打哪一种弹丸**换掉，并给持枪者挂对应自伤状态。
> LAS-17 的三档：**50 → 弹丸 189（55 伤害 / AP3）**、**100 → 222（70 / AP3）**、**190 → 26（70 / AP4）**；
> 热量低于 50 时打的是武器组件自己的基础弹丸 **151**（= LAS-16 同款 60 / AP2）；三档同时挂 **20 / 40 / 100** 自伤，
> 最高档的状态伤害行里带 **Fire** 槽 ⇒ 就是"满热自燃"。
>

## 2. 实体表侧：`HeatLevelSetting[3]`（LAS-17 的真实值）

行基址 `0x1A91ACC`（实体表 `generated_entities.dl_bin`，块 `0x4C981CD9`，row 21）。

| 档 | `+0` 阈值 (f32) | `+4` ProjectileType | `+8` u64（未解） | `+16` u32 | `+20` StatusEffectType |
|---|---|---|---|---|---|
| L1 | **50.0** | **189** | `0x0FACE9BFB1C38FE1` | 0 | **61** |
| L2 | **100.0** | **222** | `0x2ED0134A2289001D` | 0 | **62** |
| L3 | **190.0** | **26** | `0xF6305E17E32F3889` | 0 | **63** |

- 其余 **30 行**（LAS-16 / LAS-98 / LAS-7 / LAS-58 / Trident / Scythe / 相机等）三档**全 0** ⇒ 换弹丸机制是
  **通用槽位、只有 LAS-17 用了**。
- 阈值单位与 `+0x60` 过热温度同一把尺子：**200 满分，50 / 100 / 190 = 25% / 50% / 95%**。
- LAS-17 行基址处 `+0x50 = 00`（其余 30 行全是 `01`）——SDK 把它叫 `heat.overheat_lock`（满热是否锁枪/要换散热器），
  与"DE Sickle 移除全部过热保护"的官方描述一致。

## 4. 射弹表：三档弹丸是什么

`generated_projectile_settings.dl_bin`：`ProjectileSettings`（`0xBD4042C2`）= 16 B 头（`count=355`）+ **355 × 272 B**。
**行号 ≠ 枚举值**：行首 `+0x00` 才是 `ProjectileType`，所以只能按值查行。

| 角色 | 枚举值 | 行号 | 速度 | 质量 | 口径 | 倍径？ | 寿命 | `+0x3C` 伤害行 |
|---|---|---|---|---|---|---|---|---|
| 基础（与 LAS-16 共用） | **151** | 329 | 1300 | 12 | 10 | — | 6 | 55 |
| L1（热 ≥ 50） | **189** | 331 | 1300 | 12 | 10 | — | 6 | 57 |
| L2（热 ≥ 100） | **222** | 332 | 1300 | 12 | 10 | — | 6 | 58 |
| L3（热 ≥ 190） | **26** | 333 | 1300 | 12 | 10 | — | 6 | 59 |

**逐字节 diff**：三档弹丸之间**只有两处不同**——`+0x00`（自己的枚举值）与 `+0x3C`（伤害行）。
连 `+0x48`（推进器粒子）/`+0x70`（消散粒子）两个资源 id 都完全相同 ⇒ **三档外观一样，变的只是伤害**；
它们与基础弹 151 的差别则在 `+0x48`、`+0x70` 两处特效资产（热弹的弹道特效不同）。

## 6. 自伤与点燃：同一套档位挂的持枪者状态

`generated_status_effect_settings.dl_bin`：`StatusEffectSettings 0xC63E0B22` = 16 B 头 + **73 × 160 B**；
`+0x2C = DamageInfoType`（每跳伤害行）、`+0x28` 附近三个 f32 里含**时长**（本 build = 0.15 s）。

| 档 → 状态 | 行 | `+0x28` | `+0x2C` tick 伤害行 | 标准 / 耐久 | 穿甲 | 额外状态槽 |
|---|---|---|---|---|---|---|
| L1 → **61** | row 60 | 0.15 | **554** | 20 / 20 | 9 | — |
| L2 → **62** | row 61 | 0.15 | **555** | 40 / 40 | 9 | — |
| L3 → **63** | row 62 | 0.15 | **556** | **100 / 100** | 9 | **槽 1 = 类型 5（Fire）强度 10** ⇒ 自燃 |

- STATUS-EFFECTS 文档（`26088801`）全表第 61–63 行本来就写着 **Hotshot Laser Rifle (554/555/556)**，
  与本 build 逐字节一致 ⇒ 状态 id / tick 行号自 `26088801` 起没变。
- **点燃不是硬编码**：它就是 L3 状态 → tick 伤害行 556 的状态槽写死 `type=5 (Fire), 10`。
  把 L3 的状态换成 62（或 0）应该只剩重自伤、不再点燃（§10 R3）。
- 三档的自伤**只在开火且处于该档时施加**（状态时长 0.15 s，跟着射击节奏续），所以停止射击/降温即停损。

## 7. 机制总结（数据驱动的"每发一次选档"）

```
每发子弹：
  heat = 当前热量（0 .. +0x60 过热温度）
  level = 三组 HeatLevelSetting 里 threshold<=heat 的最高档；没有则用 ProjectileWeaponComponentData +0 的默认弹丸
  spawn(level.projectileType)                  # 换的是弹丸记录 ⇒ 伤害/穿甲/特效全跟着变
  if level.status != 0 and 正在开火:
      apply_status_to_wielder(level.status)    # 自伤/点燃
```

- 热量变化：`热量 += +0x74`（每发）或 `+0x78`（每秒，光束）；不开火 `-= +0x80 ×（环境系数 1.5/0.75）`。
- 达到 `+0x60` 即过热；`+0x50` 决定满热是否锁枪（LAS-17 = 不锁）。
- **整套东西没有一个"激光专用"开关**：换弹丸靠的是通用 `ProjectileType` 枚举，换伤害靠通用伤害表，自伤靠通用状态表。

## 10. 实机验证记录（单变量、按轮追加）

### 10.1 R1：LAS-17 单档换弹丸（✓ 实机 2026-11-02）

只改 LAS-17 `L1 +4`：`189 → 144`（PLAS-1 Scorcher 的弹丸；Scorcher 实体 `0xEEA5E3CEF1E12C14`，
射弹表 row 313，初速 550、命中爆炸 type 155）。阈值 50/100/190、L2/L3、三档自伤全不动。
**实机结果**：热量过 **25%（50/200）后**每一发变成等离子弹（慢、亮、命中爆炸），特效正常（驻留见 §10.4）。
⇒ "换档 = 换 `ProjectileType`" 成立，阈值生效。

### 10.2 R2：把机制搬到 LAS-16（✗ v1 → ✓ v2，选档规则由此钉死）

LAS-16 原生三档全 0，是"机制搬家"的天然靶子（它本来就有热量组件，不需要动块 0 组件清单）。

| 版本 | LAS-16 三档 `(阈值, 弹丸, 状态)` | 实机结果 |
|---|---|---|
| v1 | `(50,144,0) / (0,0,0) / (0,0,0)` | **✗ 不变**：热量过 50% 仍是自己的激光弹 |
| v2 | `(0,0,0) / (50,144,0) / (200,0,0)` | **✓ 生效**：热量过 50% 出现 Scorcher 等离子弹 |

**v1 的失败把选档模型反证出来了**：若引擎按"阈值 ≤ 热量的最高一档"，v1 的 L1(=50) 在热量过 50 后就该命中；
它没命中 ⇒ 引擎看的是**档位序号**（从高档往低判 / 数"已通过的阈值个数"），而 v1 的 L2/L3 阈值是 **0**，
永远满足、序号更高 ⇒ 直接盖掉 L1，选到空档（弹丸 0 = 不覆盖）⇒ 保持默认弹丸。

**选档规则（实机双向钉死）**

1. 阈值必须**递增**（等于把热量切成 L1 / L2 / L3 三段）；
2. 引擎取"**序号最高且阈值已满足**"的档 ⇒ 想关闭某一档，要给它一个**够不着的阈值**（> 过热温度），
   **不能填 0**（0 = 永远满足）；只有**末尾**空档可以用 0（原版 30 条热量行就是三个 0 —— 永远选到空档 = 不覆盖）；
3. 档位弹丸 = 0 表示"不覆盖"（打 `ProjectileWeaponComponentData +0` 的默认弹丸）。

**通用两档配方（本 build ✓ 实机）**

| 档 | 阈值 | 弹丸 | 状态 |
|---|---|---|---|
| L1 | `0`（或第一段分界） | `0`（不覆盖 = 武器自己的弹丸） | 0 |
| L2 | 分界热量（≤ 过热温度） | 想换的弹丸枚举（如 Scorcher 144） | 0 或所需持枪者状态 |
| L3 | **`9999`（哨兵，够不着）** | 0 | 0 |

例：LAS-16（过热 100）→ `(0,0,0) / (50,144,0) / (200,0,0)` ⇒ 0–50% 自己的弹丸、50–100% 等离子弹。
要三档全用：直接写三段递增阈值（如 25/50/75 各配一颗弹丸），不需要哨兵档。

| | LAS-22 Shear | LAS-99 Quasar / LAS-44 Nova |

### 21.1 结构读数（本 build，2026-11-03 全量解析）
| 项 | 读数 |
|---|---|
| 块 0 payload | **185,172 B = 4096 槽 × 32 B 哈希图 + 27,050 × u16 清单，恰好用满，零空位** |

### 21.2 为什么"净增一项"做不了（当前）
清单区零空位 ⇒ 想给任何实体加 1 个 u16，必须先腾出 2 字节。可选路线：

| 路线 | 做法 | 状态 |
|---|---|---|
| **替换** | 清单里把一个类型换成目标类型（count 不变、保持升序） | ✅ 结构可行（§22 采用） |
| 偷位 | 另一个实体清单少一项，然后全局偏移 +2 修正（list 起点之后所有槽的 offset 都要 +2） | ⚠ 未写工具、未验证 |
| 去重/重排 | 把某实体清单指向"内容相同"的既有清单，腾出 2 字节再重排 | ⚠ 未验证（全库清单不共享，引擎是否接受共享清单未知） |

## 25. 崩溃点反汇编：直接证据与**假设修正**（2026-11-03 夜）

> 用户问："有没有'引擎实例化时还会校验每实体已烘焙的组件数据'的直接证据？"
> 结论先给：**没有拿到"校验"的证据；反而拿到了反证，假设应修正为——
> 引擎在生成实体时会去运行期组件表里**查找它认为必然存在的组件**，查不到就产生**负 count**，
> 负 count 被当成长度传进"按属性列表累加字节尺寸"的函数 ⇒ 42 亿次循环 ⇒ 越界读 ⇒ AV。**

### 25.1 取到解密代码（磁盘 exe 是加壳的）
`helldivers2.exe` 在磁盘上**代码段被加密**（入口点字节为随机数据，静态反汇编不可行）。
但**崩溃 dump 的代码页是运行期解密后的**：从 `dump_crash.py` 的 memory ranges 直接读 `RIP` 前后字节，得到崩点指令原文。

崩点（`helldivers2.exe+0x4E7987`，dump `18.17.14`）：

```asm
mov  eax, [r11]              ; r11 = arg2->0x20：属性索引列表（u32×count）
lea  rcx, [rax+rax*2]        ; 索引 ×3
movzx eax, byte [rsi+rcx*8+0xC]   ; descA[index].byte_0xC = kind   <<< AV 越界读
cmp  eax, 0xC / ja ...
mov  ecx, [r14+rax*4+0x4E7A08] / add rcx,r14 / jmp rcx   ; 13 路跳表
```

### 25.2 整函数语义（用旧 build 全量 dump 拿到完整函数体）
`E:\hd2-dumps\kept\crash-20128-full.dmp`（11.06 GB，全量内存）里按函数头 15 字节
`40 55 48 83 EC 20 45 33 D2 48 8B E9 45 85 C0` **唯一命中**旧 exe `+0x173DE0`（当前 build 的对应函数在 `+0x4E7980`）：

```c
// 返回：前 count 个属性的字节总尺寸（用于算每个字段在动态结构里的偏移）
int64 size_of_props(Schema* arg1, Instance* arg2, int count) {
    u32* idx   = arg2->[0x20];          // 属性索引列表
    Desc* desc = arg1->[0x18|0x20];     // 24 B/项 描述符数组
    u64 total = 0;
    for (i = 0; i < count; i++) {       // ← count 为负 ⇒ 42 亿次
        u32 k = idx[i];                 // ← 崩在这里读到 0x50AC6619（不是合法索引）
        total += kind_size(desc[k].kind) + nested(desc[k]);
    }
    return total;
}
```

### 25.3 四次崩溃的确定性证据
| dump | 改动 | `rax`（读出的"索引"） | `rdi`（count） |
|---|---|---|---|
| 10-31 10:58（P-41 V2） | 蓝图 77→247 ＋ 共享行 | **0x50AC6619** | **0xFFFFFFE7（−25）** |
| 10-31 11:06（P-41 V3） | 同上 ＋ 追加独立行 | **0x50AC6619** | **0xFFFFFFE7（−25）** |
| 11-03 18:17（R7） | LAS-98 127→237 ＋ 共享行 | **0x50AC6619** | **0xFFFFFFE3（−29）** |
| 11-03 18:29（R7b） | 同上但行 289 私有 | **0x50AC6619** | **0xFFFFFFE3（−29）** |

四次 `rax` **逐位相同**、count 为**负**且按实体分组（LAS-98 恒 −29，P-41 恒 −25）
⇒ **确定性的数据错配**，不是随机坏内存；且 count 负数随实体而变 ⇒ 它由**该实体的数据**算出。

### 25.4 24 个调用点里找到负 count 的来源（直接证据）
旧 build 里对 `+0x173DE0` 共 24 个直接 `call`。其中一类（`+0x34B3CA`、`+0x34B4DA`、`+0x34B5FB`、`+0x34B85A`、
`+0x3DA8BA`、`+0x3DAB1A`、`+0x3DDB1C` 等）模式完全一致：

```asm
mov  edx, [rdi+0x18]        ; 该实体的"组件类型数量"
xor  ebx, ebx
loop: cmp [rdi+0x38 + rbx*4], eax   ; 在该实体的组件 id 数组里线性搜一个类型
      je  found
      inc ebx / cmp ebx,edx / jb loop
      mov ebx, 0xFFFFFFFF       ; ← 没找到 ⇒ ebx = -1
found: mov r8d, ebx             ; ← 直接把 -1 当 count
       call size_of_props(...)
```

⇒ **引擎在生成实体时会拿“实体运行期组件 id 数组”去查它认为应该存在的组件；查不到不报错、不兜底，
而是把 −1 当长度传下去**，于是尺寸函数循环 42 亿次并把属性索引列表当数组读 ⇒ AV。

### 25.5 假设修正：崩因更可能是"**删了组件**"，不是"加了组件"
- R7 / R7b 的改动里其实有两件事：**加 237(Targeting)** 和 **删 127(Spottable)**；
- P-41 的 V2/V3 也是 **把 77(百科) 替换成 247(Interactable)**，同样是"删了一个原本存在的组件"；
- 四次崩溃共用同一崩点、同一 `rax` 魔数 ⇒ 共同点更可能是"**某实体少了引擎认为必需的组件**"，
  而不是"多了新组件"（R7b 已证明"共享行"不是原因）。
- 与 §20 不冲突：删 **Targeting** 没事（没有代码在生成期强制查它）；但删 **Spottable/百科** 这类
  "生成/交互流程里会被查"的组件就会命中上面的 −1 路径。⚠ 该结论仍需对照实验确认（§25.6）。

### 25.8 负 count 的新解码：`~插入点`
`−29 = ~28`、`−25 = ~24`（按位取反）。这正是 **`std::lower_bound` 风格的"未命中返回 `~insertion_point`"** 约定，
而调用方（§25.4 那类搜索）**没有检查负值**就直接当 count 用 ⇒ 42 亿次循环 + 越界读。

⇒ 引擎在生成 LAS-98 时，会拿 **237** 去一个**有序的"每实体组件数组"**里查；
**该数组不认我们加进去的 237** ⇒ 未命中 ⇒ 负 count ⇒ 崩。
而这个数组**不是块 0 蓝图本身**（蓝图里已经写了 237）⇒ **引擎确实另有一份按实体的有序组件数据**（⚠ 来源未定位）；
删组件之所以安全，是因为"少一个组件"不会让这类查找命中失败路径（查的是别处要用的类型）。

⚠ 仍未证明这份数据是"烘焙"（cooked/资源层）还是运行期另行构建；但"**蓝图之外存在第二份按实体组件表**"已有**直接证据**（负 count 只能由"数组里没有该类型"产生）。

## 35. `0x4008` 到底是谁调用的？—— 全链路追踪（并纠正一处误标）

### 35.1 字段纠正

初版把 `0x4008` 写成「行 215 `+0x34` 槽1 的 `StatusEffectType`」是**错的**（行基址算错）。
本 build 伤害表数组 **base = 0x64**、stride 76：

```
0x4008 - 0x64 = 0x3FA4 = 16292 = 214 × 76 + 28
⇒ 伤害行 214，字段 +0x1C (= +28) = demo（破坏力）
```

- 行 214：`DamageInfoType 217`，`damage=1550 durable=930`，`AP=[5,5,5,0]`，`demo=30`，`force=40`，`impulse=25`，
  `element=0`，**4 个状态槽全 0**（`{0,0} ×4`）⇒ **该行不施加任何状态，"槽1"不存在**。
- `+0x1C = demo` 已用 `damage-row-map.json` 三例交叉验证：AR-11/AR-2/SG-8 的 `demolition` 都=10，本表 +28 也都=10 ✓。

### 35.2 谁调用它：唯一链 Apex AMW-20 → 弹丸 277 → 伤害 217

| 层 | 表 | 记录 | 字段 | 值 |
|---|---|---|---|---|
| 实体 | `generated_entities` · `ProjectileWeaponComponentData`（0x45171B68） | 行 268 | `+0x000` ProjectileType | **277** |
| 弹丸 | `generated_projectile_settings`（0xBD4042C2，272 B/行） | 行 255（`type=277`） | `+0x3C` DamageInfoType | **217** |
| | | | `+0x90 / +0x9C` 命中/到期爆炸 | 0 / 0（纯直伤，无爆炸） |

| 伤害 | `generated_damage_settings`（0xE0A72CF0，76 B/行） | 行 214（`type=217`） | `+0x1C` **demo** | **30**（26088801 是 15） |

- **实体名**：`0xB814EECE17533BC4` = **AMW-20 Apex**，`kind=support_weapon`，
  `loadout_tags=[TEAM WEAPON, LIGHT ANTI-TANK]`，有 `EncyclopediaEntryComponentData` 名称、
  有 `LoadoutPackage`（`0xA193A00CE4BBD529`）与 `LoadoutEntry`（`0xB7BB43D5`）⇒ **已上线武器**。

### 35.3 结论：谁调用 `demo`，谁调用状态槽

- `demo`（破坏力）**只在命中结算时被破坏管线读取**（打建筑/虫洞/工厂这类"要破坏力"的目标），
  **启动期不参与任何查表** ⇒ 它差 15↔30 **不可能造成启动黑屏**（初版的"加载期状态引用"解释作废）。
- 伤害行的 4 个状态槽只在**该行伤害被施加时**由伤害系统逐个套用；本行 4 槽全 0 ⇒ 不会有任何状态被调用。
  这也正是 `dmg_row_edit.py` 挑"没人引用的孤儿行空槽"当哈希校正字的原因（`dmg_refs` 报 187 个孤儿行、87 个可用宿主）。

### 37.1 结论：热量行的 `StatusEffectType` = 通用"效果插槽"

- 同一把武器三档可挂**三种完全不同的状态**，且**视觉全部跟随**（Gas 绿雾 / Stim 治疗 / Fire 燃烧）。
  ⇒ `HeatLevelSetting.StatusEffectType` 是决定"该档表现"的唯一指针；状态行决定 tick 伤害、视觉资源与音效。

  伤害行槽只决定"命中时施加哪个状态"，不决定"状态长什么样"。
  ⇒ §33.4 的 ⚠ 结案：**不是 Electric 没有视觉，而是改错了字段**。若要电击视觉，改**热量行状态指针**再测即可（可选）。
- 实用模板：想给任意热量武器做"分档状态玩法"（低热毒气/中热自愈/高热燃烧），只需改热量行 `+0x14/+0x2C/+0x44` 三个 u32。

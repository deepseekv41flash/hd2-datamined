# LAS-17 高/中/低热档换弹丸：热量机制全解（build `26251122`）

> **一句话**：激光武器的"弹匣"是热量槽（`WeaponHeatComponentData`）。**LAS-17 是全游戏唯一**把热量组件里
> 3 组 `HeatLevelSetting` 填了值的武器——每组 = `{温度阈值, 该档换用的 ProjectileType, 挂给持枪者的 StatusEffectType}`。
> 引擎按当前热量选"阈值 ≤ 热量"的最高档，把**这一发打哪一种弹丸**换掉，并给持枪者挂对应自伤状态。
> LAS-17 的三档：**50 → 弹丸 189（55 伤害 / AP3）**、**100 → 222（70 / AP3）**、**190 → 26（70 / AP4）**；
> 热量低于 50 时打的是武器组件自己的基础弹丸 **151**（= LAS-16 同款 60 / AP2）；三档同时挂 **20 / 40 / 100** 自伤，
> 最高档的状态伤害行里带 **Fire** 槽 ⇒ 就是"满热自燃"。
>

## 2. 实体表侧：`HeatLevelSetting[3]`（LAS-17 的真实值）

行基址 `0x1A91ACC`（实体表 `generated_entities.dl_bin`，块 `0x4C981CD9`，row 21）。

| 档 | `+0` 阈值 (f32) | `+4` ProjectileType | `+8` u64（未解） | `+16` u32 | `+20` StatusEffectType |
|---|---|---|---|---|---|
| L1 | **50.0** | **189** | `0x0FACE9BFB1C38FE1` | 0 | **61** |
| L2 | **100.0** | **222** | `0x2ED0134A2289001D` | 0 | **62** |
| L3 | **190.0** | **26** | `0xF6305E17E32F3889` | 0 | **63** |

- 其余 **30 行**（LAS-16 / LAS-98 / LAS-7 / LAS-58 / Trident / Scythe / 相机等）三档**全 0** ⇒ 换弹丸机制是
  **通用槽位、只有 LAS-17 用了**。
- 阈值单位与 `+0x60` 过热温度同一把尺子：**200 满分，50 / 100 / 190 = 25% / 50% / 95%**。
- LAS-17 行基址处 `+0x50 = 00`（其余 30 行全是 `01`）——SDK 把它叫 `heat.overheat_lock`（满热是否锁枪/要换散热器），
  与"DE Sickle 移除全部过热保护"的官方描述一致。

## 4. 射弹表：三档弹丸是什么

`generated_projectile_settings.dl_bin`：`ProjectileSettings`（`0xBD4042C2`）= 16 B 头（`count=355`）+ **355 × 272 B**。
**行号 ≠ 枚举值**：行首 `+0x00` 才是 `ProjectileType`，所以只能按值查行。

| 角色 | 枚举值 | 行号 | 速度 | 质量 | 口径 | 倍径？ | 寿命 | `+0x3C` 伤害行 |
|---|---|---|---|---|---|---|---|---|
| 基础（与 LAS-16 共用） | **151** | 329 | 1300 | 12 | 10 | — | 6 | 55 |
| L1（热 ≥ 50） | **189** | 331 | 1300 | 12 | 10 | — | 6 | 57 |
| L2（热 ≥ 100） | **222** | 332 | 1300 | 12 | 10 | — | 6 | 58 |
| L3（热 ≥ 190） | **26** | 333 | 1300 | 12 | 10 | — | 6 | 59 |

**逐字节 diff**：三档弹丸之间**只有两处不同**——`+0x00`（自己的枚举值）与 `+0x3C`（伤害行）。
连 `+0x48`（推进器粒子）/`+0x70`（消散粒子）两个资源 id 都完全相同 ⇒ **三档外观一样，变的只是伤害**；
它们与基础弹 151 的差别则在 `+0x48`、`+0x70` 两处特效资产（热弹的弹道特效不同）。

## 6. 自伤与点燃：同一套档位挂的持枪者状态

`generated_status_effect_settings.dl_bin`：`StatusEffectSettings 0xC63E0B22` = 16 B 头 + **73 × 160 B**；
`+0x2C = DamageInfoType`（每跳伤害行）、`+0x28` 附近三个 f32 里含**时长**（本 build = 0.15 s）。

| 档 → 状态 | 行 | `+0x28` | `+0x2C` tick 伤害行 | 标准 / 耐久 | 穿甲 | 额外状态槽 |
|---|---|---|---|---|---|---|
| L1 → **61** | row 60 | 0.15 | **554** | 20 / 20 | 9 | — |
| L2 → **62** | row 61 | 0.15 | **555** | 40 / 40 | 9 | — |
| L3 → **63** | row 62 | 0.15 | **556** | **100 / 100** | 9 | **槽 1 = 类型 5（Fire）强度 10** ⇒ 自燃 |

- STATUS-EFFECTS 文档（`26088801`）全表第 61–63 行本来就写着 **Hotshot Laser Rifle (554/555/556)**，
  与本 build 逐字节一致 ⇒ 状态 id / tick 行号自 `26088801` 起没变。
- **点燃不是硬编码**：它就是 L3 状态 → tick 伤害行 556 的状态槽写死 `type=5 (Fire), 10`。
  把 L3 的状态换成 62（或 0）应该只剩重自伤、不再点燃（§10 R3）。
- 三档的自伤**只在开火且处于该档时施加**（状态时长 0.15 s，跟着射击节奏续），所以停止射击/降温即停损。

## 7. 机制总结（数据驱动的"每发一次选档"）

```
每发子弹：
  heat = 当前热量（0 .. +0x60 过热温度）
  level = 三组 HeatLevelSetting 里 threshold<=heat 的最高档；没有则用 ProjectileWeaponComponentData +0 的默认弹丸
  spawn(level.projectileType)                  # 换的是弹丸记录 ⇒ 伤害/穿甲/特效全跟着变
  if level.status != 0 and 正在开火:
      apply_status_to_wielder(level.status)    # 自伤/点燃
```

- 热量变化：`热量 += +0x74`（每发）或 `+0x78`（每秒，光束）；不开火 `-= +0x80 ×（环境系数 1.5/0.75）`。
- 达到 `+0x60` 即过热；`+0x50` 决定满热是否锁枪（LAS-17 = 不锁）。
- **整套东西没有一个"激光专用"开关**：换弹丸靠的是通用 `ProjectileType` 枚举，换伤害靠通用伤害表，自伤靠通用状态表。

## 10. 实机验证记录（单变量、按轮追加）

### 10.1 R1：LAS-17 单档换弹丸（✓ 实机 2026-11-02）

只改 LAS-17 `L1 +4`：`189 → 144`（PLAS-1 Scorcher 的弹丸；Scorcher 实体 `0xEEA5E3CEF1E12C14`，
射弹表 row 313，初速 550、命中爆炸 type 155）。阈值 50/100/190、L2/L3、三档自伤全不动。
**实机结果**：热量过 **25%（50/200）后**每一发变成等离子弹（慢、亮、命中爆炸），特效正常（驻留见 §10.4）。
⇒ "换档 = 换 `ProjectileType`" 成立，阈值生效。

### 10.2 R2：把机制搬到 LAS-16（✗ v1 → ✓ v2，选档规则由此钉死）

LAS-16 原生三档全 0，是"机制搬家"的天然靶子（它本来就有热量组件，不需要动块 0 组件清单）。

| 版本 | LAS-16 三档 `(阈值, 弹丸, 状态)` | 实机结果 |
|---|---|---|
| v1 | `(50,144,0) / (0,0,0) / (0,0,0)` | **✗ 不变**：热量过 50% 仍是自己的激光弹 |
| v2 | `(0,0,0) / (50,144,0) / (200,0,0)` | **✓ 生效**：热量过 50% 出现 Scorcher 等离子弹 |

**v1 的失败把选档模型反证出来了**：若引擎按"阈值 ≤ 热量的最高一档"，v1 的 L1(=50) 在热量过 50 后就该命中；
它没命中 ⇒ 引擎看的是**档位序号**（从高档往低判 / 数"已通过的阈值个数"），而 v1 的 L2/L3 阈值是 **0**，
永远满足、序号更高 ⇒ 直接盖掉 L1，选到空档（弹丸 0 = 不覆盖）⇒ 保持默认弹丸。

**选档规则（实机双向钉死）**

1. 阈值必须**递增**（等于把热量切成 L1 / L2 / L3 三段）；
2. 引擎取"**序号最高且阈值已满足**"的档 ⇒ 想关闭某一档，要给它一个**够不着的阈值**（> 过热温度），
   **不能填 0**（0 = 永远满足）；只有**末尾**空档可以用 0（原版 30 条热量行就是三个 0 —— 永远选到空档 = 不覆盖）；
3. 档位弹丸 = 0 表示"不覆盖"（打 `ProjectileWeaponComponentData +0` 的默认弹丸）。

**通用两档配方（本 build ✓ 实机）**

| 档 | 阈值 | 弹丸 | 状态 |
|---|---|---|---|
| L1 | `0`（或第一段分界） | `0`（不覆盖 = 武器自己的弹丸） | 0 |
| L2 | 分界热量（≤ 过热温度） | 想换的弹丸枚举（如 Scorcher 144） | 0 或所需持枪者状态 |
| L3 | **`9999`（哨兵，够不着）** | 0 | 0 |

例：LAS-16（过热 100）→ `(0,0,0) / (50,144,0) / (200,0,0)` ⇒ 0–50% 自己的弹丸、50–100% 等离子弹。
要三档全用：直接写三段递增阈值（如 25/50/75 各配一颗弹丸），不需要哨兵档。

| | LAS-22 Shear | LAS-99 Quasar / LAS-44 Nova |

## 19. LAS-22 的 `TargetingComponent` 与别人有什么不一样（2026-11-03）

块 `0x2C0968D2` / 行类型 `0x5E30EC98` / 64 B / 全库 **297 行、71 种不同签名**。

**LAS-22 这一行（row 289）的字段**（有 SDK 佐证的语义已标注）：

| 偏移 | 值 | 说明 |
|---|---|---|
| `+0x00` f32 | **25.0** | 目标搜索距离（推断） |
| `+0x04/+0x08/+0x0C` f32 | **0.5 / 0.5 / 5.0** | **三个计时器** —— HD2Runtime 文档明写 "TargetingComponent timers (0.5 / 0.5 / 5 s on every sentry)" ✔ |
| `+0x10/+0x14` f32 | 90 / 180 | 视场/锥角类参数（推断：半角/全角，度） |
| `+0x18` u8 | **1** | 开关位（297 行中 109 行为 1；同组有 Rocket Devastator / War Strider / Reinforced Scout Strider） |
| `+0x1C` u32 | **0x4A182741** | 目标分类/过滤档位（哈希）：该值被 **84 个实体共用**（HMG/AT Emplacement、SAM、Autocannon/Mortar Sentry、Caustic Spewer…），不是 LAS-22 独有 |

| `+0x3C..+0x3F` u8×4 | 1,1,1,0 | 四个开关位 |

**和别人的差异**

1. **数值上不特殊**：LAS-22 的这套数值（25 / 0.5 / 0.5 / 5 / 90 / 180 / (1,0,-1) / 0x4A182741 / [1,1,1,0]）
   与 **13 个实体完全相同**（含 Wretch、Crusher 和若干未命名实体），是典型的"炮台/自动瞄准"通用档。
2. **特殊的是"它出现在一把手持主武器上"**：297 个带 TargetingComponent 的实体里
   - **58 个是炮台/固定武器**（哨戒、HMG/AT 阵地、防空、炮塔…）；
   - 其余是敌人单位/道具；
   - **手持实体只有 4 个**：`Seeker`、`Anti-Tank Seeker`、`Larva Container`、**`Shear`(LAS-22)** —— **LAS-22 是唯一的手持武器**。
3. 这解释了它为什么"能吐弹"以及"2877 搬到别的武器就崩"：**这台武器天生带"自己找目标"的组件**，
   满热那一发很可能就是靠它选目标/给方向的；把 2877 塞给没有 TargetingComponent 的普通枪（LAS-98/LAS-16），
   能力代码拿不到目标数据 ⇒ 空指针崩溃（⚠ 仍为推断，未取崩溃日志）。
   若要真正移植，就得给目标武器补 `TargetingComponent`——仍卡在实体块 0 组件清单写法（未解）。

## 21. 块 0 组件清单的写入边界：**删已解，净增仍未解**（2026-11-03 解析）

> 回答用户追问"块 0 组件清单写法不是还没解明吗"：**是，只解了"删"**。今日解析把"加"的硬约束量化如下。

### 21.1 结构读数（本 build，2026-11-03 全量解析）
| 项 | 读数 |
|---|---|
| 块 0 payload | **185,172 B = 4096 槽 × 32 B 哈希图 + 27,050 × u16 清单，恰好用满，零空位** |
| 清单区 | 起始 131,072（=哈希图末尾），最后一个清单结束 185,172（=payload 末尾），**完全紧排无空隙** |
| 有清单的实体 | **1,939**；`sum(count) = 27,050`（一个不多一个不少） |
| 清单形态 | **升序**、单条清单内无重复 |
| u16 的语义 | **组件类型编号**（不是实例）：322 个不同值，最大 326 |
| 类型编号 → 块 | 254 个唯一命中、28 个"同键集同名块"歧义、40 个无 key→row 块 |
| 组件块自己的哈希图 | 272 个块带「实体键 → 行」哈希图，合计 24,545 行；**全库零"两键共用一行"** |

### 21.2 为什么"净增一项"做不了（当前）
清单区零空位 ⇒ 想给任何实体加 1 个 u16，必须先腾出 2 字节。可选路线：

| 路线 | 做法 | 状态 |
|---|---|---|
| **替换** | 清单里把一个类型换成目标类型（count 不变、保持升序） | ✅ 结构可行（§22 采用） |
| 偷位 | 另一个实体清单少一项，然后全局偏移 +2 修正（list 起点之后所有槽的 offset 都要 +2） | ⚠ 未写工具、未验证 |
| 去重/重排 | 把某实体清单指向"内容相同"的既有清单，腾出 2 字节再重排 | ⚠ 未验证（全库清单不共享，引擎是否接受共享清单未知） |
| 搬块长行 | 把索敌块移到文件末尾再 +64 B，加一条私有行 | ⚠ 需 21 MB 搬移，未验证 |

### 21.3 索敌块的行资源现状（决定了 R7 只能共享行）
